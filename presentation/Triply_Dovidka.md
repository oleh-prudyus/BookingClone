# Загальна довідка по проєкту Triply

## Про проєкт

**Triply** — веб-платформа для бронювання готелів і транспортних квитків (аналог Booking.com з розширеним функціоналом продажу квитків на потяги та автобуси між містами).

Три ролі користувачів:
- **Клієнти (Customer)** — пошук і бронювання готелів та транспорту, чат із власниками, керування своїми бронюваннями.
- **Власники / реалтори (Realtor)** — додають готелі, керують номерами й цінами, спілкуються з клієнтами в чаті.
- **Адміністратори (Admin)** — модерація контенту, керування користувачами, загальна статистика платформи.

## Технологічний стек

**Frontend**
- React + TypeScript
- Ant Design (UI-компоненти)
- react-router-dom (маршрутизація, включно з синхронізацією фільтрів пошуку в URL через `useSearchParams`)
- Модульна архітектура на кшталт Feature-Sliced Design: `app / pages / widgets / features / entities / shared`
- Чистий SPA (без SSR/prerender) — без JavaScript сторінка не рендериться

**Backend**
- .NET, Clean Architecture: `Domain → Application → Infrastructure → API`
- CQRS через MediatR (Commands/Queries/Handlers) + FluentValidation у pipeline
- Repository pattern поверх Entity Framework Core
- JWT-автентифікація з refresh-токенами; авторизація через ролі (`[Authorize(Roles = ...)]`)
- OpenAPI/Swagger для документації API

**База даних та інфраструктура**
- PostgreSQL (Neon — хмарний managed Postgres)
- Docker / docker-compose для контейнеризації всіх сервісів (api, frontend, db, umami-аналітика)

## Масштаб проєкту (факти з коду)

- **31** контролер, **143** REST API endpoints
- **44** Domain-сутності, **43** таблиці в базі даних
- **84** Command + **59** Query + **145** Handler (CQRS/MediatR)
- **15+** репозиторіїв поверх EF Core

## Архітектура backend

Чотири незалежні шари (окремі проєкти):
- **Domain** — бізнес-сутності, не залежить ні від чого зовнішнього
- **Application** — бізнес-логіка, use-case'и (Commands/Queries/Handlers)
- **Infrastructure** — робота з БД, зовнішні сервіси, репозиторії
- **API** — HTTP-контролери, вхідна точка застосунку

Залежності спрямовані всередину (Infrastructure → Application → Domain), що дозволяє змінювати зовнішні деталі (наприклад, СУБД) без впливу на бізнес-логіку.

## Архітектура frontend

- `app` — конфігурація застосунку, роутинг, провайдери
- `pages` — сторінки застосунку
- `widgets` — великі складені блоки інтерфейсу
- `features` — окремі функціональні модулі (логін, чат, бронювання тощо)
- `entities` — бізнес-сутності на фронтенді
- `shared` — перевикористовувані компоненти, утиліти, UI-кіт

## База даних

Спрощено, ключові сутності: **AppUser** (базова автентифікація) → **Customer** / **Realtor** (ролі). Клієнт пов'язаний з **Booking**, **Chat**, **Ticket**; реалтор — з **Hotel** і **Chat**. Далі йде деталізація: варіанти номерів, повідомлення чату, транспортні маршрути, а також довідники міст і країн.

## Ключовий функціонал

- Реєстрація та авторизація з розділенням ролей
- Пошук і фільтрація готелів (з URL-станом фільтрів)
- Детальні сторінки готелів з номерами та варіантами бронювання
- Пошук транспортних квитків між містами
- Повний цикл бронювання
- Чат між клієнтами й власниками в реальному часі (SignalR)
- Адмін-панель для модерації платформи
